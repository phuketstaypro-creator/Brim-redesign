# Доступность

## Статус

Цель frontend — WCAG 2.2 AA. Это цель проверки, а не заявление о достигнутом соответствии.

`package.json` предоставляет `npm run test:a11y` на базе Playwright/axe и отдельный `npm run test:visual`, но автоматические scanners покрывают только часть требований. Ручные проверки screen reader, keyboard, zoom, reflow, cognitive clarity и доступности документов должны быть выполнены отдельно на финальном deployment.

Текущие PDF/документы отсутствуют, поэтому их доступность не проверена. CMS content и будущие редакционные материалы также могут ухудшить результат независимо от качества шаблона.

Все 73 маршрута текущего local bundle содержат основной HTML без зависимости от JavaScript. Иерархическая навигация также присутствует в server-rendered `<details>/<summary>`; client script только координирует раскрытие, Escape и возврат фокуса. Страницы с `structureOnly: true` имеют читаемое предупреждение об отсутствии утверждённых материалов. Такое предупреждение предотвращает ложное представление данных, но само по себе не делает обязательный раздел содержательно или юридически полным.

## Контентный контракт

При интеграции CMS редактор обязан:

- сохранять логичную иерархию заголовков без выбора уровня ради размера;
- заполнять содержательный `coverAlt`/`alt` для информативной фотографии и не полагаться на общий `defaultAlt`, если конкретный контекст требует другого описания;
- оставлять пустой alt только у действительно декоративного изображения;
- не дублировать подпись дословно в alt без необходимости;
- писать осмысленный текст ссылки вместо «сюда» или полного URL;
- указывать язык фрагмента, если он отличается от русского;
- использовать поддержанные rich-text blocks (`heading`, `paragraph`, `quote`, `list`, `link`) вместо raw HTML и сохранять логичную outline внутри уровней `h2`/`h3`;
- использовать списки и таблицы семантически; текущий rich-text renderer поддерживает списки, но не table block, поэтому таблица требует согласованного расширения и новых тестов;
- не передавать смысл только цветом, положением или формой карточки;
- добавлять captions/transcript для будущих аудио и видео;
- проверять каждый загружаемый документ отдельно.

Контент ссылается на изображения по строгим media ID. Build отклоняет неизвестный ID, проверяет контейнер и реальные размеры каждого локального rendition, материализует variants и выводит intrinsic `width`/`height`, но не может проверить смысл alt. Карточка без подтверждённой фотографии намеренно рендерится без `<img>`; нельзя подставлять чужой cover только ради визуального заполнения.

Imported Yandex photos имеют pending-final-rights-check status. Доступностная проверка alt не заменяет проверку права публикации и согласий изображённых лиц.

## Обязательные автоматические проверки

```bash
npm ci
npm run build
npm run test
npm run test:e2e
npm run test:a11y
npm run test:visual
```

Перед релизом сохранить версию браузера/axe и результаты. Целевое условие для axe: 0 critical и 0 serious violations на согласованном наборе страниц и состояний. Нулевой результат axe не равен полной сертификации.

Текущий `test:a11y` автоматически сканирует `/`, `/education/`, `/news/`, `/sveden/`, `/sveden/common/`, `/sveden/managers/`, `/students/psychological-service/` и `/sitemap/` на critical/serious axe violations. Отдельно сканируются раскрытые desktop- и mobile-состояния группы «Сведения». Это зафиксированное автоматическое покрытие, а не полный release audit.

Перед релизом покрыть дополнительно:

- одну news article и каждый новый template, добавленный CMS;
- `/documents/`;
- `/privacy/`;
- `404.html`;
- открытые menu, search и accessibility dialog states.

Если CMS добавляет event routes, sample event page также входит в обязательную матрицу. Employee renderer уже выводит CMS-записи на `/sveden/employees/`; при подключении реальных данных этот маршрут требует отдельного сценария с фото, должностями и keyboard navigation.

## Keyboard checklist

1. Начать с обновления страницы, не используя мышь.
2. Проверить видимость и работу skip link.
3. Пройти Tab/Shift+Tab через utility navigation, header, main и footer.
4. Убедиться, что порядок фокуса совпадает с визуальным и DOM-порядком.
5. Раскрыть каждую группу иерархического меню клавишами Enter/Space; убедиться, что её ссылки становятся доступны по Tab, а другая группа закрывается предсказуемо.
6. Нажать Escape в раскрытой группе: группа должна закрыться, а фокус — вернуться на её `<summary>`.
7. Открыть/закрыть mobile menu клавишами Enter/Space и Escape; после закрытия фокус должен вернуться на кнопку меню.
8. Открыть search/accessibility dialogs, проверить начальный фокус, focus containment, Escape и возврат фокуса на trigger.
9. Проверить все controls и ссылки на различимость focus indicator.
10. Убедиться, что скрытая панель не получает фокус.
11. Проверить отсутствие keyboard trap.

Результат документируется по браузеру, ОС и устройству ввода. Исправление только mouse behavior не закрывает keyboard defect.

## Screen reader checklist

Минимум один Windows screen reader (например, NVDA) и VoiceOver на доступной Apple-платформе:

- корректный русский язык документа;
- понятный title каждой страницы;
- один `h1` и логичная heading outline;
- landmarks header/nav/main/footer;
- breadcrumbs с текущим элементом;
- доступные имена menu/search/accessibility controls;
- объявления открытого/закрытого состояния каждой navigation-группы и понятные названия её `<summary>`;
- точный `aria-current="page"` только на ссылке текущего маршрута, включая элементы вложенного меню и боковой директории `/sveden/`;
- понятный DOM-порядок news cards независимо от двухколоночной masonry-композиции;
- дата новости читается как дата, а не декоративный набор;
- изображения имеют ожидаемый alt;
- сообщения поиска объявляются без потери фокуса;
- 404 явно называется страницей, которой нет.

Версию assistive technology и найденные ограничения сохранить в отчёте.

## Reflow, zoom и responsive

Проверить ширины:

```text
320, 360, 390, 768, 1024, 1440, 1920 px
```

Отдельно проверить browser zoom 200% и 400%. Критерии:

- нет горизонтального scrolling для основного текста и controls;
- header/menu не перекрывают содержимое;
- focus не скрывается за sticky elements;
- текст не обрезается;
- buttons и links не накладываются;
- новостная композиция остаётся читаемой и сохраняет естественный DOM-order;
- portrait/landscape/square/featured/no-media cards не создают layout shift;
- content доступен при отключённых изображениях;
- размеры touch targets проверены вручную.

## Настройки отображения

Frontend предусматривает size, theme, images, spacing и motion preferences с локальным хранением. Для каждого режима проверить:

- фактическое визуальное изменение, а не только состояние кнопки;
- `aria-pressed` выбранного значения;
- читаемость текста и controls;
- сохранение после reload;
- доступный reset;
- корректную работу без localStorage;
- отсутствие обязательной анимации при reduced motion или motion off.

LocalStorage настройки интерфейса не доказывает правовое или accessibility соответствие само по себе.

## Цвет и motion

- Проверить contrast обычной, monochrome и high-contrast схем инструментом и вручную.
- Проверить text over image во всех реальных crop variants.
- Focus indicator должен быть виден на тёмном и светлом фоне.
- Не полагаться только на hover.
- `prefers-reduced-motion` и ручное отключение motion должны исключать несущественные transitions/animations.

## Документы

Каждый PDF/скан проходит отдельную проверку: text layer, теги, порядок чтения, заголовки, язык, таблицы, alt, bookmarks и контраст. Если исходный документ недоступен, нужна доступная HTML-альтернатива либо документированный план remediation владельцем контента.

Frontend-тесты не могут автоматически сделать загруженный CMS PDF доступным.

## Приёмочный отчёт

Текущий `test:visual` пишет screenshots основных страниц и состояний на mobile/desktop, включая `/sveden/`, `/sitemap/`, детальный обязательный подраздел и раскрытую группу «Сведения», а также меню и панель доступности в `artifacts/screenshots/`. Перед снимком он прокручивает lazy media и проверяет broken images, overflow, console errors и page errors. Эти файлы помогают regression-проверке, но не являются автоматическим pixel-diff baseline и не заменяют review реального deployment.

Для релиза сохранить:

- commit SHA и deployment URL;
- список проверенных маршрутов/states;
- axe output;
- screenshots 390/1440;
- keyboard checklist;
- screen reader/OS/browser versions;
- zoom/reflow results;
- список исключений и владельца каждого исправления;
- отдельный статус документов и CMS content.

Без этих результатов следует писать «подготовлено с учётом доступности», а не «полностью соответствует WCAG».
